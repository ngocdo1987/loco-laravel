# Auth module

`src/modules/auth/` is the reference implementation of this project's
[module convention](modules.md). It owns everything related to user
accounts: password + magic-link authentication exposed as a JSON API, the
same authentication exposed as server-rendered web pages, the `users`
entity's business logic, the auth-related emails, and the `user:create` CLI
task.

## File map

```
src/modules/auth/
  mod.rs          AuthModule (Module trait impl) — registers 2 route groups
  routes.rs       routes()      -> /api/auth/*  (JSON)
                  web_routes()  -> /login, /register, /logout, /dashboard (Tera)
  controllers.rs  JSON API handlers
  web.rs          Browser-facing page handlers (Tera + cookie session)
  requests.rs     All request/param structs (LoginParams, RegisterParams, ForgotParams, ...)
  views.rs        JSON response shapes (LoginResponse, CurrentResponse)
  mailer.rs       AuthMailer (welcome / forgot-password / magic-link emails)
  mailer/         Tera templates for the 3 emails above (html.t/text.t/subject.t each)
  tasks.rs        UserCreate — `cargo loco task user:create`
  models/
    mod.rs
    users.rs      ActiveModelBehavior + all business-logic methods on `Model`/`ActiveModel`
```

The generated Sea-ORM entity itself (`users::{Model, ActiveModel, Entity}`
struct/column definitions) is **not** in this module — it lives in the
shared `src/models/_entities/users.rs`, regenerated by `cargo loco db
entities`. `src/modules/auth/models/users.rs` only adds hand-written
behavior on top of it (see [modules.md](modules.md#what-stays-sharedflat-and-why)
for why entities stay outside the module).

## Data model (`users` table)

| Column | Type | Notes |
|---|---|---|
| `id` | `i64` | primary key |
| `pid` | `Uuid` | public identifier (JWT subject, used in URLs/responses instead of `id`) |
| `email` | `String` (unique) | |
| `password` | `String` | bcrypt/argon-hashed via `loco_rs::hash` — never stored or logged in the clear |
| `api_key` | `String` (unique) | generated on insert (`lo-<uuid>`), used by the `Authenticable` API-key auth path |
| `name` | `String` | validated (min 2 chars) in `before_save` |
| `reset_token` / `reset_sent_at` | `Option` | forgot-password flow |
| `email_verification_token` / `email_verification_sent_at` / `email_verified_at` | `Option` | signup verification flow |
| `magic_link_token` / `magic_link_expiration` | `Option` | passwordless login flow |

`ActiveModelBehavior::before_save` (in `models/users.rs`) validates
name/email on every save and, on insert, sets `pid` and `api_key`.

Business-logic methods on `Model`/`ActiveModel` (all in `models/users.rs`,
called from both the API and the web controllers — see "Reuse" below):

| Method | Purpose |
|---|---|
| `Model::find_by_email` / `find_by_pid` / `find_by_api_key` | lookups |
| `Model::find_by_verification_token` / `find_by_reset_token` / `find_by_magic_token` | token lookups, with expiration checks for reset (30 min) and magic-link (5 min) tokens |
| `Model::verify_password` | bcrypt-verify a plaintext password |
| `Model::create_with_password` | hash + insert; returns `ModelError::EntityAlreadyExists` on duplicate email |
| `Model::generate_jwt` | issue a JWT for the user's `pid` |
| `ActiveModel::set_email_verification_sent` / `verified` | signup verification flow |
| `ActiveModel::set_forgot_password_sent` / `reset_password` | forgot-password flow |
| `ActiveModel::create_magic_link` / `clear_magic_link` | magic-link flow |

## JSON API (`/api/auth/*`, `routes()` in `routes.rs`)

| Method | Path | Handler | Behavior |
|---|---|---|---|
| POST | `/register` | `register` | create user, send welcome email; always returns `200 {}` even on failure (doesn't reveal *why* registration failed) |
| GET | `/verify/{token}` | `verify` | mark the account verified |
| POST | `/login` | `login` | password login → `{token, pid, name, is_verified}` |
| POST | `/forgot` | `forgot` | issue a reset token + email; always `200 {}` (doesn't reveal whether the email exists) |
| POST | `/reset` | `reset` | consume the reset token, set a new password |
| GET | `/current` | `current` | current user, requires `Authorization: Bearer <jwt>` (or wherever `auth.jwt.location` in config points) |
| POST | `/magic-link` | `magic_link` | issue a magic-link token + email; only allowed for `@example.com`/`@gmail.com` (see "Known limitations") |
| GET | `/magic-link/{token}` | `magic_link_verify` | consume the magic-link token → JWT |
| POST | `/resend-verification-mail` | `resend_verification_email` | re-send the welcome/verification email if not yet verified |

## Web pages (`web_routes()` in `routes.rs`, handlers in `web.rs`)

Root-level (not under `/api`), Tera-rendered, modeled after the `web/`
auth-controller branch of this team's `goravel` reference project. See
[`plans/auth_web_ui.md`](../plans/auth_web_ui.md) for the full design
rationale.

| Method | Path | Guard | Behavior |
|---|---|---|---|
| GET | `/login` | redirect to `/dashboard` if already logged in | render `assets/views/auth/login.html` |
| POST | `/login` | same | authenticate; success → cookie + redirect `/dashboard`; failure → re-render with `error` + sticky `email` |
| GET | `/register` | redirect to `/dashboard` if already logged in | render `assets/views/auth/register.html` |
| POST | `/register` | same | create user, send welcome email, log in immediately; duplicate email → "Email already registered"; other failure → generic error |
| POST | `/logout` | none | clear the cookie, redirect to `/login` |
| GET | `/dashboard` | redirect to `/login` if not logged in | render `assets/views/auth/dashboard.html` with name/email/pid |

**No separate session system.** "Logged in" for these pages means: an
`auth_token` cookie is present and holds a JWT that
`loco_rs::auth::jwt::JWT::validate` accepts — the exact same JWT the JSON
API issues, just carried in a cookie (`HttpOnly`, `SameSite=Lax`) instead of
a response body. `web.rs`'s `current_web_user()` helper does this
check-and-load in one place; every handler above calls it.

**Reuse, not duplication**: every one of the web handlers calls the exact
same `Model`/`AuthMailer` methods listed above — `find_by_email` +
`verify_password`, `create_with_password`, `generate_jwt`,
`AuthMailer::send_welcome` — that `controllers.rs` and `tasks.rs` also call.
Only the request parsing (`Json<T>` vs `Form<T>`) and the response shape
(JSON body vs render-or-redirect+cookie) differ between the API and web
layers.

## Mailer

`AuthMailer` (`mailer.rs`) sends three emails, each with its own
`mailer/<name>/{html,text,subject}.t` Tera template directory:

| Method | Template dir | Sent from |
|---|---|---|
| `send_welcome` | `mailer/welcome/` | `register`, `resend_verification_email`, `web::register_submit`, `tasks::UserCreate` |
| `forgot_password` | `mailer/forgot/` | `forgot` |
| `send_magic_link` | `mailer/magic_link/` | `magic_link` |

The three `static ... Dir<'_> = include_dir!(...)` paths in `mailer.rs` are
crate-root-relative string literals — if this module is ever renamed, these
(and the physical `mailer/` folder) must move and be updated together.

## Task

`cargo loco task user:create email:<e> name:<n> password:<p>` (`tasks.rs`,
registered in `src/app.rs`'s `register_tasks`) creates a user the same way
`register` does (`create_with_password` + `set_email_verification_sent` +
`send_welcome`) — useful for seeding an account without going through HTTP.

## Known limitations / deliberate omissions

- **No CSRF protection** on the web forms — Loco has no built-in CSRF
  middleware to hook into, and adding one was out of scope for this
  feature (see `plans/auth_web_ui.md`).
- **Magic-link email allowlist** (`EMAIL_DOMAIN_RE` in `controllers.rs`,
  `@example.com`/`@gmail.com`) is a starter placeholder — tighten or
  replace it before relying on this flow in a real deployment.
- **No web forgot/reset/profile pages** — only login, register, logout,
  and a minimal dashboard exist on the web side, mirroring exactly what
  the `goravel` reference project's own `web/` controllers cover. The
  forgot/reset flow is only reachable via the JSON API today.
- Most failure paths (`register`, `forgot`, `resend-verification-mail`)
  deliberately return a generic `200 {}` from the JSON API regardless of
  the real reason, to avoid leaking whether an email exists in the
  database. The web register form is the one exception (see "Web pages"
  above) — it does reveal "Email already registered", matching the
  `goravel` reference UX and standard signup-form practice.

## Extending this module

Adding a new auth-related endpoint (JSON or web) or a new email: follow the
[general module checklist](modules.md#create-a-new-module--checklist), but
since `auth` already exists you're just adding a file/route to it rather
than creating a new module — e.g. a new mailer method goes in `mailer.rs`
(+ a new `mailer/<name>/` template dir), a new web page goes in `web.rs` +
`routes.rs`'s `web_routes()`, a new request shape goes in `requests.rs`.
